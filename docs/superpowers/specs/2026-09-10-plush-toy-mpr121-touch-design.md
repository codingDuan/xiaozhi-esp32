# 毛绒玩具触摸感知设计方案（MPR121）

**日期**：2026-09-10
**目标硬件**：ESP32-S3 面包板开发板，板型 `plush-toy`
**新增外设**：MPR121 12 通道电容式接近/触摸传感器模块，I2C 接口
**前置状态**：舵机（PCA9685）与双眼屏已实机可用；HTTP 文本动作测试通道已在 8181 端口运行

---

## 1. 目标与范围

给玩具加上被动触摸感知：人碰到玩具，玩具知道。

本期交付四种响应模式，可叠加，运行时切换：

| 模式 | 语义 |
|---|---|
| 本地反射 | 不经服务端，直接改眼睛表情并触发手臂动作 |
| 唤醒对话 | 触摸代替唤醒词，直接进入聆听状态 |
| 上报大模型 | 把触摸作为上下文送给服务端，由模型决定如何回应 |
| 读值诊断 | 通过 HTTP 读出电极原始计数、基线与触摸位，用于标定阈值 |

### 明确不在本期范围内

- 区分点击、长按、连续抚摸。本期事件词汇只有**碰到**和**离开**两种。
- 多电极布线。驱动按 12 通道实现，但本期只接**一个头部电极**跑通链路。
- 接近感应（未接触即感知）。MPR121 有这个能力，但阈值标定依赖实际布料厚度和电极面积，等单电极跑通后再谈。
- MPU6050 姿态传感器。已记录在 `plans/TODO.md` 的 D4。

## 2. 硬件约束

### 2.1 引脚：无空闲，因此不接 IRQ

ESP32-S3 可用引脚已全部占满：GPIO0-21 被摄像头、双眼屏、麦克风、喇叭、舵机 I2C 和原生 USB 占完，GPIO38-48 被屏 SPI、SPI CS、音频和控制台 TX 占完，GPIO26-32 是 flash，GPIO33-37 被八线 PSRAM 占用（`sdkconfig` 中 `CONFIG_SPIRAM_MODE_OCT=y`）。

**结论**：MPR121 的 IRQ 引脚接不上，只能轮询。

这个代价可以接受，因为去抖由芯片内部的 `DEBOUNCE` 寄存器（0x5B）完成，软件侧只需比较触摸状态位的变化，不需要自己维护去抖定时器。50ms 轮询下每秒 20 次两字节读，相对舵机脉宽写入的总线占用可以忽略。

### 2.2 总线：并入 I2C_NUM_0

MPR121 的 SDA/SCL 直接并到现有舵机总线上，不需要任何新引脚。

| 设备 | 地址 | 备注 |
|---|---|---|
| PCA9685 | 0x40 | 已在用 |
| MPR121 | 0x5A | ADDR 引脚接地时的默认地址 |
| MPU6050 | 0x68 | 未来，见 TODO D4 |

三者不冲突。总线速率保持 100kHz（`SERVO_I2C_HZ`）。

### 2.3 供电：VCC 必须接 3V3

**模块的 VCC 接 ESP32 的 3V3，不要接 5V。** MPR121 模块的 I2C 上拉电阻拉到它自己的 VCC，若 VCC 是 5V，SCL（GPIO3）和 SDA（GPIO44）会被拉到 5V，超出 ESP32-S3 的引脚耐压。GPIO3 还是 JTAG_SEL 启动引脚，被外部拉高会改变复位时的 JTAG 选择。

2026-09-10 已因电源接反烧过一次教训，此处不重复。

## 3. 架构

沿用现有的三层结构，与 `Pca9685` → `LimbController` → `PlushBehavior` 同构。

```
Mpr121            纯寄存器驱动，不含任何行为语义
  ↓  轮询
TouchController   任务：轮询、比较状态位、产出 碰到/离开 事件
  ↓  回调
PlushBehavior     持有模式掩码，按掩码分发到眼睛 / 手臂 / 状态机 / 服务端
```

评估过的另外两种接法及否决理由：

| 方案 | 描述 | 否决理由 |
|---|---|---|
| B | 把轮询塞进 `PlushBehavior` 现有的 100ms 状态循环 | 驱动与行为耦合，主机测试无法脱开行为层单独跑驱动；采样率被行为循环绑死 |
| C | 触摸事件进 FreeRTOS 队列，另设消费者 | 触摸事件处理本身不耗时，队列是多余的间接层 |

**采纳 A 的理由**：每一层都能单独测试，且与现有分层一致，读代码的人不需要学第二套结构。

### 3.1 Mpr121

职责：把寄存器读写包装成有意义的操作。不知道电极对应身体哪个部位，不知道触摸意味着什么。

接口：

- `Init()` —— 复位并写入配置序列，末尾**回读校验**
- `ReadTouchBits()` —— 返回 12 位触摸状态
- `ReadFiltered(ch)` / `ReadBaseline(ch)` —— 标定阈值用的原始值
- `Diagnostics()` —— 一行文本，格式对齐 `Pca9685::Diagnostics()`

回读校验沿用 `Pca9685::Init()` 的做法：写完阈值后读回一个寄存器比对，不一致就判定芯片未正确响应并返回失败。MPR121 没有 WHO_AM_I 寄存器，回读是唯一可靠的在线验证手段。

初始化寄存器序列取自 NXP AN3944，具体数值见实现，**阈值必须在实机标定后回填**：布料厚度和电极面积会显著改变触发点，出厂默认值几乎肯定不合适。这正是"读值诊断"模式存在的理由。

### 3.2 TouchController

职责：轮询与事件产出。

- 独立任务，50ms 周期，优先级与 `LimbController` 同级
- 每次读 12 位触摸状态，与上一次比较
- 某位由 0 变 1 → 碰到事件；由 1 变 0 → 离开事件
- 不做软件去抖，去抖交给芯片的 0x5B 寄存器

### 3.3 PlushBehavior

新增触摸事件入口，持有模式掩码，按位分发。四条路径互不影响，一次触摸可以同时走多条。

本期的本地反射映射（单电极，头部）：碰到时眼睛切到 `happy`，手臂做一次欢呼；离开时眼睛回 `neutral`。

## 4. 配置与观测

### 4.1 模式掩码

位掩码存 NVS，运行时可改，改完立即生效且重启保持。使用现有的 `Settings` 封装，命名空间 `plush`，键名 `touch_modes`。

| 位 | 值 | 模式 |
|---|---|---|
| 0 | 0x01 | 本地反射 |
| 1 | 0x02 | 唤醒对话 |
| 2 | 0x04 | 上报大模型 |
| 3 | 0x08 | 读值诊断 |

默认值 `0x09`，即本地反射加读值诊断：开箱能动、能读，但不打扰对话流程。读值诊断位只控制是否把原始计数放进 `status` 返回，不影响事件产出。

### 4.2 观测通道必须走 HTTP，不能走日志

**这是硬性约束，不是偏好。** 板子的应用层控制台输出目前是哑的：2026-09-10 用官方 `esp-idf-monitor` 抓过 30 秒，`entry 0x403c88f4` 之后一个字节都没有，重新烧录后依然如此，而设备的 Wi-Fi 和 HTTP 一直正常。原因尚未查明，已知与舵机电源接反无关。

因此 `diagnostics` 那种"打一行日志"的做法拿不到任何结果。触摸标定所需的原始值必须从 `/test/v1/status` 返回。

本期扩展该端点的返回，带上：触摸位、每个电极的滤波计数与基线、当前模式掩码。顺带把 PCA9685 的诊断也从日志里救出来，让现有的 `diagnostics` 动作真正可用。

### 4.3 测试通道新增动作

- 读模式掩码：并入扩展后的 `status` 返回
- 写模式掩码：新增一个测试动作
- 模拟触摸：新增一个测试动作，不碰硬件也能验证四条响应路径。这条对回归很关键 —— 否则每跑一次回归都要有人伸手去摸玩具。

## 5. 错误处理

**触摸链路的任何失败都不得影响对话。** 与舵机链路同一原则：探测不到芯片、初始化失败、轮询读失败，全部只记状态并让 `mpr121_` 保持 `nullptr`，绝不 `ESP_ERROR_CHECK`。没有触摸的玩具仍应能正常说话、动手臂、眨眼。

轮询中途读失败不重试、不退出任务：保留上一次的触摸状态，下个周期再读。I2C 偶发失败在共享总线上是正常的，为此杀掉任务得不偿失。

## 6. 测试策略

### 6.1 主机侧

新增 `test/test_mpr121.cc`，沿用 `test_pca9685` 的 stub 模式，覆盖：配置序列写入正确、回读校验失败时 `Init` 返回 false、触摸位解析、滤波值与基线的字节序。

`test/test_http_channel.cc` 扩充：新增动作进白名单、非法动作仍被拒。

`TouchController` 的状态位比较逻辑独立于硬件，应可在主机上直接测边沿检测：无变化不产生事件、单位翻转产生单个事件、多位同时翻转产生多个事件。

### 6.2 实机验收

1. `status` 能读到电极的滤波计数与基线，且手指靠近时计数明显变化。这一条不过，阈值无从标定。
2. 用实机读数标定触摸/释放阈值并回填代码。
3. 四种模式逐一单独验证，再验证叠加。
4. 触摸期间连续做手臂动作，确认共享 I2C 总线上没有互相干扰。
5. 拔掉 MPR121 模块，确认设备仍能正常对话和做动作。

## 7. 未决事项

- 阈值的最终数值，依赖实机标定。
- 电极扩展到多点后的事件语义，等单点跑通再设计。
- 应用层控制台静默问题的根因。它不阻塞本期交付（观测走 HTTP），但会持续降低所有后续排查的效率。
