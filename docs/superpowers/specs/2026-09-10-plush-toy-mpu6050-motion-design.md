# 毛绒玩具运动感知设计方案（MPU6050）

**日期**：2026-09-10
**目标硬件**：ESP32-S3 面包板开发板，板型 `plush-toy`
**新增外设**：MPU6050 六轴姿态传感器模块（GY-521），I2C 接口
**前置状态**：舵机（PCA9685）与触摸（MPR121）已并入 `I2C_NUM_0` 并实机可用

---

## 1. 目标与范围

让玩具感知自己被怎么对待：被摇晃，以及当前是竖着、躺倒还是倒置。

本期交付驱动、判定、观测通道，以及一套默认反射行为。响应模式沿用触摸那套四位掩码的形状，但**用独立的 NVS 键**，以便单独关掉其中一类传感器。

### 明确不在本期范围内

- **陀螺仪**。姿态由重力方向得出，摇晃由加速度幅值判定，两者都不需要角速度。少读 6 字节，也少一组要标定的参数。寄存器随时可以加，现在加就是 YAGNI。
- **拍打与碰撞检测**。瞬时加速度尖峰与舵机自身振动难以区分，等摇晃的抑制机制被实机验证过再谈。
- **被抱起与放下**。语义诱人，但可靠判定依赖持续的竖直加速度积分，噪声敏感；且抱住玩具会同时压到多个触摸电极，与触摸侧尚未决策的部位映射（`plans/TODO.md` D5）耦合。
- **自由落体、计步等 MPU6050 的其他能力。**

## 2. 硬件约束

### 2.1 引脚：无空闲，因此不接 INT

引脚状况与接入 MPR121 时相同：GPIO0-21 与 38-48 已占满，26-32 是 flash，33-37 被八线 PSRAM 占用。MPU6050 的 INT 引脚接不上，只能轮询。

姿态与摇晃都不需要毫秒级响应，轮询完全够用。

### 2.2 总线：并入 I2C_NUM_0

| 设备 | 地址 |
|---|---|
| PCA9685 | 0x40 |
| MPR121 | 0x5A |
| MPU6050 | 0x68 |

三者不冲突。AD0 接地或悬空即为 0x68，GY-521 模块内部已下拉。

只读加速度计的 6 个字节，100ms 一次，相对舵机脉宽写入与触摸轮询的带宽占用可以忽略。

### 2.3 供电与上拉：新增风险

**VCC 接 3V3，不要接 5V。** 模块自带稳压，芯片本身能吃 5V，但它的 I2C 上拉是拉到 VCC 引脚电压的，接 5V 会把 SDA(GPIO44)、SCL(GPIO3) 拉到 5V。

**总线上拉会变强，这是接入 MPU6050 特有的新风险。** GY-521 板载 4.7k 上拉，比 PCA9685 与 MPR121 的 10k 低一倍。三块板并联后总上拉约 2.4k，再叠上 ESP32 内部上拉会更低。100kHz 下预期仍可工作，但若接入后出现 I2C 读写失败，或现有的触摸、舵机开始不稳，**第一件事是拆掉 GY-521 上那两颗上拉电阻**。

## 3. 架构

沿用已有的三层结构，与 `Mpr121` → `TouchController` → `PlushBehavior` 同构。

```
Mpu6050           纯寄存器驱动，只吐三轴原始加速度
  ↓  轮询
MotionController  任务：轮询、姿态判定（带迟滞）、摇晃判定（带不应期）
  ↓  回调
PlushBehavior     持有 motion_modes 掩码，按位分发
```

不再评估其他分层：触摸接入时已经比较过「塞进现有循环」和「事件队列」两种做法并否决，理由同样适用，重复评估没有价值。

### 3.1 Mpu6050

职责：唤醒芯片并读原始加速度。不知道什么是摇晃，不知道什么是倒置。

- `Init()` —— 解除睡眠、设置量程，末尾**回读校验**。MPU6050 有 `WHO_AM_I`（0x75，应读回 0x68），比 MPR121 的处境好，但仍需回读一个自己写过的寄存器来确认写通路，只读 `WHO_AM_I` 无法区分「能读不能写」。
- `ReadAccel(int16_t& x, int16_t& y, int16_t& z)` —— 一次突发读 6 字节，避免三轴来自不同采样时刻。
- `Diagnostics()` —— 一行文本，格式对齐 `Pca9685::Diagnostics()` 与 `Mpr121::Diagnostics()`。

量程选 ±4g：±2g 在摇晃时会削顶，±8g 及以上牺牲静态姿态的分辨率。

### 3.2 MotionController

职责：把原始加速度翻译成两类事件。轮询周期 100ms。

**姿态**取重力矢量方向，分竖着、躺倒、倒置三态。

判定必须带**迟滞**：玩具斜靠在沙发上时，重力矢量正好落在两态边界，没有迟滞会反复横跳，每次横跳都会改一次眼睛表情。做法是进入某态与离开该态用不同的角度门限。

姿态是状态不是脉冲，**只在跨态时产生一次事件**。

**摇晃**取加速度幅值对 1g 的偏离，在滑动时间窗内累计超过阈值的次数，达标产生一次事件后进入**不应期**。

不应期是必须的：一次持续两秒的摇晃若不加抑制会刷出几十个事件，眼睛和手臂会被刷爆。

### 3.3 舵机自振的抑制

**这是运动感知特有的问题，触摸那边不存在。** 手臂动作产生的机械振动会被加速度计读到，可能被判为摇晃 —— 而摇晃的默认反射又是摆手，可能自激。

做法：给 `LimbController` 加 `busy()`，动作执行期间及结束后一小段窗口内**抑制摇晃判定**。姿态判定不抑制，它看的是静态重力，不受振动影响。

## 4. 配置与观测

### 4.1 模式掩码

形状与触摸一致，但用**独立的 NVS 键**，命名空间 `plush`，键名 `motion_modes`。独立的理由是调试时要能单独关掉一类传感器。

| 位 | 值 | 模式 |
|---|---|---|
| 0 | 0x01 | 本地反射 |
| 1 | 0x02 | 唤醒对话 |
| 2 | 0x04 | 上报大模型 |
| 3 | 0x08 | 读值诊断 |

默认 `0x09`，与触摸一致：开箱能动、能读，不打扰对话流程。

上报位与唤醒位仍是包含关系：上报走 `WakeWordInvoke`，本身带唤醒效果，两位同开不会触发两轮对话。这一点与 `PlushBehavior::OnTouch` 的处理保持一致。

### 4.2 默认反射

使用**现有**的眼睛预设，不新增情绪。`eye_display.cc` 的 21 个预设里没有 `dizzy`。

| 事件 | 眼睛 | 手臂 |
|---|---|---|
| 摇晃 | `confused` | 摆手一次 |
| 进入倒置 | `surprised` | 不动 |
| 进入躺倒 | `sleepy` | 不动 |
| 回到竖着 | `neutral` | 不动 |

姿态变化不带手臂动作：姿态改变往往发生在玩具被搬动时，此时动手臂既容易卡住又浪费电流。

### 4.3 观测走 HTTP

理由同触摸：应用层控制台完全静默（`plans/TODO.md` 技术债），打日志的诊断拿不到结果。

`status` 扩展带出：三轴原始加速度、当前姿态、摇晃窗口内的计数、`motion_modes`。

### 4.4 测试通道新增动作

- `motion_modes`：写掩码
- `simulate_motion`：不碰硬件产生一次摇晃或一次姿态变化，用于回归四条响应路径

## 5. 错误处理

与舵机、触摸同一原则：探测不到、初始化失败、轮询读失败，全部只记状态并让 `mpu6050_` 保持 `nullptr`，绝不 `ESP_ERROR_CHECK`。没有运动感知的玩具仍须能对话、动手臂、眨眼、感知触摸。

轮询读失败不重试不退出，保留上一次判定结果，下个周期再读。

**读失败不得被当成读数。** `Mpr121::ReadFiltered` 读失败返回 0，实机标定时确实混进过 0 值样本。加速度的 0 是合法值，因此 `ReadAccel` 用返回值 `bool` 报告成败，不用哨兵值。

## 6. 测试策略

### 6.1 主机侧

- `test_mpu6050.cc`：沿用 `test_mpr121` 的 fake I2C 与冻结寄存器手法。覆盖初始化序列、回读校验失败、三轴大端拼接与符号、读失败时 `ReadAccel` 返回 false 且不改写出参。
- `test_motion_controller.cc`：判定逻辑不碰硬件，直接喂加速度序列。覆盖：稳定竖直不产生事件；跨过门限产生一次且仅一次姿态事件；边界附近抖动因迟滞不产生事件；连续摇晃在不应期内只产生一个事件；抑制开启时摇晃不产生事件而姿态照常。
- `test_http_channel.cc`：新动作进白名单，非法动作仍被拒。

### 6.2 实机验收

1. `status` 中 `motion_present` 为 true。为 false 先查接线与 VCC 电压。
2. 三轴读数随姿态变化，静置时合矢量接近 1g。这一条不过，阈值无从标定。
3. 标定摇晃阈值与姿态门限并回填，重新烧录。
4. 三种姿态各停留几秒，确认事件只在跨态时产生一次。
5. 玩具斜靠不同角度，确认没有反复横跳。
6. 触发一次手臂动作，确认不产生摇晃事件。
7. 拔掉 MPU6050 重启，确认对话、手臂、眼睛、触摸全部照常。
8. 三块 I2C 设备同时工作，确认触摸与舵机未因总线上拉变化而退化。

## 7. 未决事项

- 摇晃阈值、姿态门限、迟滞宽度、不应期时长的最终数值，依赖实机标定。
- 默认反射映射很可能在触摸部位映射决策（`plans/TODO.md` D5）时被一并重写。
- 总线上拉并联后的实际表现，需在三块设备同时在线时观察。
