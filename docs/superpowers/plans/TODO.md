## D. 需要硬件或网络环境配合

### D1. 舵机 trim 校准
`0°` 是电气中位，装到手臂上后「自然下垂」未必对应 0°。建议存 NVS `Settings` 以便在线调整而不重烧。

### D2. 独立 5V 电源 + 1000µF 电容
**实测**：USB 供电下双路舵机无间歇连续动作会 BROWNOUT 掉电重启（可复现两次）。目前靠动作间强制冷却 300ms 规避。装进玩偶后手臂带载，电流更大，独立电源成为必需。

### D3. 服务端固定地址
服务端 IP 随网络变化，症状是「设备突然不说话」。本次已为此绕了三轮。

**已选本地方案**：使用 Mac 的 Bonjour 名称 `MacBook-Pro-107.local`。本机验证该名称当前可解析到 `10.35.80.13`；固件构建配置已启用 `CONFIG_LWIP_DNS_SUPPORT_MDNS_QUERIES=y`，服务端也允许显式配置完整 WebSocket/视觉 URL。

迁移时把设备 NVS 中的 OTA 地址配为 `http://MacBook-Pro-107.local:8003/xiaozhi/ota/`，并把服务端 `data/.config.yaml` 的地址改为 `ws://MacBook-Pro-107.local:8010/xiaozhi/v1/` 与对应的 `:8003/mcp/vision/explain`。当前没有直接修改运行配置：设备仍需重新配网，且手机热点是否转发 mDNS 必须在现场验证；若热点隔离 mDNS，则改用路由器 DHCP 地址保留或公网域名。

### D5. MPR121 电极部位映射未定
**2026-09-10 实机接线**：接了 8 路（ELE1、2、4、6、7、9、10、11），未接 4 路（ELE0、3、5、8）。但**每个电极贴在玩具哪个部位尚未确定**，需后续决策。

在此之前有两处代码是错的，不要以为它们已经成立：

- `config.h` 的 `TOUCH_HEAD_ELECTRODE` 仍是 0，而 ELE0 根本没接线。这个常量目前只被诊断读数用到，还没有真正的语义。
- `PlushBehavior::OnTouch()` 对所有电极执行同一套反射（眼睛变 happy + 手臂欢呼）。只有一个电极时无所谓，8 个电极下必须先有部位语义才能设计行为。

决策时需要一并回答：哪些部位共用一种反应、哪些各自不同；多个电极同时被触摸（抱住玩具会同时压到多处）时如何取舍，是取第一个、取优先级最高的，还是合成一个「被抱住」的复合事件。

### D6. MPR121 的 ELE1 与 ELE2 无响应
**2026-09-10 实测**：这两路已接线，但 60 秒采样中从未被判定为触摸，最大偏移仅 27 和 11，而正常电极触摸时偏移 124 到 158。

症状形态是**恒定偏移而非触摸尖峰**：ch1 全程稳定低 14 到 27，ch2 稳定低 7 到 11，从第一秒持续到最后一秒，与是否触摸无关。说明这两路被持续加载 —— 引线碰到其他导体，或电极片压在金属、潮湿填充物上。芯片的基线跟踪会把恒定偏移吸收掉，因此不报触摸，手指再叠加也顶不出足够增量。

排查方向：先断开这两根引线单独量电极对地电容，再检查走线是否与舵机线或屏 SPI 线并行贴合。

### D3b. I2C 总线坏读（优先级高于所有标定）
**2026-09-10 实测基线**：坏帧率约 **8.8%** —— 设备侧 `motion_rejected` 计数 25 秒新增 22 帧，轮询 100ms 一帧。典型坏样本 `accel=[3073,-1,-1]`、`[3095,-515,-515]`、`az=-258`，形态是全 1 或接近全 1 的字节，说明从机传输中途停止驱动 SDA。

**这个毛病早于 MPU6050 接入**：触摸标定时（当时 MPU6050 尚未接线）同样出现过 `touch_filtered` 读到 0 和撕裂值。是总线的电气问题，不是某个设备的问题。

**当前元器件全在面包板上，尚未装进实物**，飞线长且走线杂乱，这本身就是坏读的典型成因。装配后很可能自行改善，因此**不要在面包板阶段花时间标定任何阈值**——装配会改变电极电容、模块朝向和走线，标定结果全部作废。

判定层已有防御（合理性闸门 + 姿态连续三帧确认，见 `motion_controller.cc`），但残余风险仍在：落在合理区间内的坏样本会制造摇晃命中，每秒约一帧坏数据，凑满三次即误报摇晃。

可试的手段，由易到难：拆掉 GY-521 板载的两颗 4.7k 上拉；`SERVO_I2C_HZ` 从 100kHz 降到 50kHz；缩短飞线并把 SDA 与 SCL 分开走。用 `status` 的 `motion_rejected` 增长速度对比效果。

### D4. MPU6050 阈值实机标定
**代码已完成**：驱动、姿态与摇晃判定、模式掩码、默认反射、舵机自振抑制、HTTP 观测、模拟运动，主机侧十项测试全绿。尚未接线，以下参数全是猜测值，必须实机标定后回填：

| 参数 | 当前值 | 说明 |
|---|---|---|
| `MOTION_SHAKE_DELTA` | 0.35g | 合矢量对 1g 的偏离门限 |
| `MOTION_SHAKE_HITS` | 3 | 窗口内命中次数 |
| `MOTION_SHAKE_WINDOW_MS` | 1000 | 滑动窗口 |
| `MOTION_SHAKE_COOLDOWN_MS` | 1500 | 不应期 |
| 姿态四门限 | ±0.7g / ±0.5g | 进入与离开，构成迟滞 |
| `MOTION_SERVO_SETTLE_MS` | 400 | 动作后的沉降窗口 |
| `MOTION_UP_AXIS_Z` | 1 | 装配后若姿态判反改这里 |

**标定时注意一个已知陷阱**：摇晃判定看的是合矢量对 1g 的偏离，**缓慢倾斜也会被记为命中**。静态停在 0.6g 时偏离已达 0.4g，超过默认阈值，连续三次即误判为摇晃。这个性质是主机测试写迟滞用例时暴露的，不是推测。

标定方法见 `main/boards/plush-toy/README.md` 的「运动标定」。
